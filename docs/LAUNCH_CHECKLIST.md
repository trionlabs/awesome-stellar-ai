# Public Launch Checklist

The repository stays private during editorial incubation. Going public should be a quality event, not merely a visibility toggle.

## Publication Gate

- [ ] Every README entry has a matching evidence-catalog record.
- [ ] Every material maturity or network claim has a direct public source.
- [ ] No private, inaccessible, archived, or placeholder repository is listed.
- [ ] Two consecutive weekly link-health runs pass without unexplained failures.
- [ ] `awesome-lint` and catalog validation pass on `main`.
- [ ] Governance, contribution, conduct, and conflict-of-interest policies reflect the actual maintainer workflow.
- [ ] Repository description and topics are current.
- [ ] At least one person other than the author has reviewed the taxonomy and ten randomly selected entries.
- [ ] The first public announcement explains the scope and evidence standard, not only the number of projects.

## Distribution Strategy

1. Publish the repository and invite corrections from the listed project maintainers first.
2. Share it with Stellar developer and agent-payment communities as a maintained reference.
3. Ask official documentation maintainers to consider it as a community resource only after the first correction cycle.
4. Invite listed projects to use the optional “Mentioned in Awesome Stellar AI” badge after their entry is confirmed.
5. Use hackathon retrospectives as discovery inputs, then evaluate projects under the normal criteria.

The central `sindresorhus/awesome` index currently rejects blockchain-related lists. Do not make inclusion there a launch dependency. The stronger distribution wedge is trust from Stellar builders and project maintainers.

## Deferred Until Public Evidence Exists

Projects and standards under private development stay outside the README until their primary implementation or technical documentation is publicly accessible. Grant or hackathon status alone does not satisfy the publication gate.
